Community & Control Plane

Free, open-source MySQL and MariaDB backup

Free, open-source MySQL and MariaDB backup: mysqldump or mariadb-dump into encrypted snapshots. Restore a dropped table through a side database.

Community Documentation Community Docs
Control Plane Documentation Control Plane Docs

MySQL and MariaDB commit every schema change, even from a failed migration

Each ALTER TABLE or DROP TABLE is committed on its own. A migration that fails halfway leaves the schema half changed, with no transaction to roll back, and replicas apply the same statements within seconds.

The binary log can replay up to the mistake only while it is kept, 30 days by default.

Plakar loads the dump taken before the migration into a side database, under another name, next to production. You copy back what was lost, and the rest of the server keeps its writes.

Overview

What the MySQL and MariaDB integration does

The MySQL integration backs up MySQL and MariaDB servers, self-hosted or managed, by running mysqldump or mariadb-dump and storing the SQL output as an encrypted Plakar snapshot. It restores into any running server, under the original database name or another one, so a dropped table comes back through a side database next to production. Plakar runs on any host that reaches the server and has the matching client tools, with the free, open-source CLI or with Plakar Control Plane.

Three protocols cover the common setups. mysql:// drives the MySQL client tools, mysqldump for backup and mysql for restore. mysql+mariadb:// drives mariadb-dump and mariadb, so a MariaDB server is always dumped by MariaDB’s own tool. mysql+gcsql:// reaches Google Cloud SQL for MySQL through the Cloud SQL Go connector, with Application Default Credentials and no Auth Proxy to run.

Each snapshot holds the dump, either one database as <name>.sql or the whole server as all.sql, and a manifest.json written before the dump starts. InnoDB tables are read in a single consistent transaction, and the application keeps writing while the dump runs.

Why Plakar

Why use Plakar for MySQL and MariaDB backup

no agent

No package on the MySQL host

Plakar reaches the server over the MySQL protocol, like any client. It runs on a backup host, in a container or on an edge, and the database machine keeps its packages, its my.cnf and its change process.

stdout → snapshot

MySQL dumps streamed with no staging disk

The output of mysqldump flows straight into the snapshot. A 500 GB schema does not need 500 GB of free space on the backup host, and no dump file waits in /tmp for a cleanup job.

mysql < shop.sql

Plain SQL, readable without Plakar

Every dump is the text file mysqldump writes. Load it with the mysql client, search it with grep, or pull one table out of it by hand. Nothing proprietary stands between you and your data.

shop → shop_restore

Restore a MySQL database under any name

A single-database dump carries no USE statement, so it loads into whatever database the destination names. Bring yesterday’s shop back as shop_restore on the production server and copy rows across with SQL.

Recovery scenarios

MySQL and MariaDB backup and recovery scenarios

DROP TABLE customers;

An AI agent drops the MySQL customers table

A coding agent asked to “clean up unused tables” runs its migration against production and drops customers. Every replica applies the DROP TABLE from the binary log. With a plakar backup taken before the session, and the store and passphrase never in the agent’s environment, load the earlier snapshot into a side database and copy customers back with the steps below. The tables the agent changed on purpose keep its work, and plakar diff -recursive between the two snapshots shows what the session touched.

binlog_expire_logs_seconds

A bad MySQL UPDATE found after the binlog expired

A bulk UPDATE products SET price = ... with the wrong filter ran six weeks ago. MySQL 8.0 and 8.4 keep binary logs for 30 days by default (binlog_expire_logs_seconds=2592000), so nothing is left to replay up to the moment before it. Nightly snapshots cost little after deduplication. Restore the dump from before the change into a staging database and compare the rows with production.

ALTER TABLE … ERROR 1062

A MySQL schema migration fails halfway

MySQL commits each DDL statement on its own, so a migration that stops at its fourth ALTER TABLE leaves the first three applied and no transaction to roll back. A snapshot taken by the deploy pipeline just before the migration holds the schema and data as they were, ready to load into a side database or into a rebuilt one.

project:region:instance

Moving a managed MySQL database to another host

The automated backups of a managed MySQL service restore inside that service. On Google Cloud SQL, mysql+gcsql:// dumps the instance by its connection name, such as my-project:europe-west1:orders, and a mysql:// destination loads the dump into any other MySQL server, self-hosted or at another provider.

Dropped table

How to restore a dropped table in MySQL

MySQL has no undo for DROP TABLE. With a snapshot of the shop database taken before the drop, the table comes back through a side database on the same server, and production keeps every write made since.

Find the snapshot from before the drop. plakar ls lists the snapshots with their dates, and the manifest of the one you pick lists customers among the tables of shop.

Load it into a side database. A destination with create_db=true creates shop_restore and loads the dump into it. The dump of a single database holds no USE statement, so nothing touches shop.

Copy the table back. Recreate customers from its definition in shop_restore and copy its rows with INSERT ... SELECT.

Drop the side database. Once the application reads the table again, remove shop_restore.

Shell 
$ plakar at /var/backups ls
$ plakar at /var/backups cat 8c41d0a9:/manifest.json

$ plakar destination add shopside \
    mysql://root@db.example.com/shop_restore \
    password=secret create_db=true
$ plakar at /var/backups restore -to "@shopside" 8c41d0a9

$ mysql -u root -p -e "
    CREATE TABLE shop.customers LIKE shop_restore.customers;
    INSERT INTO shop.customers SELECT * FROM shop_restore.customers;
    DROP DATABASE shop_restore;"

Three connectors

MySQL backup methods: mysql://, mysql+mariadb:// and mysql+gcsql://

mysql://

MySQL with mysqldump

Any MySQL server reachable over the network, self-hosted or managed. One database, or the whole server with --all-databases. Restores go through the mysql client.

Shell 
plakar source add shop \
  mysql://backup@db.example.com/shop \
  password=secret
mysql+mariadb://

MariaDB with mariadb-dump

The same backup driven by MariaDB’s own mariadb-dump and mariadb clients. Point mariadb_bin_dir at the binaries when several client versions live on the backup host.

Shell 
plakar source add wiki \
  mysql+mariadb://backup@mariadb.example.com/wiki \
  password=secret
mysql+gcsql://

Cloud SQL for MySQL by connection name

Plakar opens the encrypted connection itself through the Cloud SQL Go connector and authenticates with Application Default Credentials. host holds the instance connection name.

Shell 
plakar source add orders \
  mysql+gcsql://backup@localhost/orders \
  host=my-project:europe-west1:orders \
  password=secret

What the dump holds Tables, views, routines, triggers and events of shop Every database, the mysql system database included
Accounts and grants Stay on the target server as they are Restored with the mysql system database

Teams often run both: one source per application database for fast, targeted restores, and a nightly whole-server source that captures accounts and grants.

Recovery objectives

MySQL backup strategy: RPO, RTO and what to restore

A MySQL backup plan starts from two numbers. The recovery point objective (RPO) is how much recent data the business can afford to lose. The recovery time objective (RTO) is how long it can wait for the data to come back. A third question sets what each source must cover: what you need to bring back.

What you must recover Snapshot that holds it How it comes back
A whole server after a host loss A whole-server source, /all.sql A mysql:// destination on a new server, accounts included
One application database One source per database, /<name>.sql Under its own name or a new one with create_db=true
One dropped table The database’s snapshot from before the drop A side database, then INSERT ... SELECT
Rows changed by a bad UPDATE The snapshot from before the change A side database, then a row-by-row comparison

The RPO sets the schedule. A one-hour RPO means a plakar backup every hour, from cron or from a Plakar Control Plane policy. The RTO comes from a measured restore, which the restore drill below gives you on a server of the same size.

Built on MySQL practice

MySQL and MariaDB backup best practices built in

The integration ships with the settings MySQL administrators add to mysqldump by hand.

A consistent InnoDB dump without stopping writes.

single_transaction=true is the default, so InnoDB tables are read from one consistent snapshot while the application keeps writing.

Stored procedures, functions and events in the dump.

mysqldump leaves out routines and events unless asked. The integration passes --routines and --events, and keeps triggers, by default.

A dump tool that matches the server.

mysql:// and mysql+mariadb:// each call their own binaries, and mysql_bin_dir or mariadb_bin_dir pins the exact client. The manifest records which tool and version made each dump.

GTIDs handled on purpose.

set_gtid_purged is passed to mysqldump. Set it to OFF for dumps meant to load into another server with its own GTID history.

Copies away from the database host.

Put the store on another disk, an S3-compatible bucket or an SFTP host, in another account or site, and keep a second copy with plakar sync.

Backups you have checked.

plakar check verifies the integrity of every snapshot without restoring it.

Restore drills on a staging server.

Restore the latest snapshot into shop_staging with create_db=true every week. The drill proves the dump loads, times the restore against your RTO, and gives staging current production data in the same run.

No backup credentials on the database server.

Run Plakar on a separate backup host. The MySQL server then holds neither the credentials of the store nor its passphrase, so an intruder on the database host finds no key to the snapshots there.

A passphrase the whole on-call rotation can reach.

Snapshots open only with the store passphrase. Keep it in a secret manager that every on-call engineer can read, so a restore never waits for the person who set up the backups.

Inside a snapshot

What a MySQL or MariaDB backup snapshot contains

A snapshot is a small tree you can browse with plakar ls, and every file in it opens with the MySQL tools you already run.

manifest.json is written before the dump. It records the server version and the version of mysqldump or mariadb-dump, whether the server was read-only (is_read_replica), settings such as gtid_mode, binlog_format, sql_mode and character_set_server, and for each database its tables with engine, row estimate, columns, indexes and constraints, plus routines, triggers and events. Whole-server snapshots also list user accounts with their authentication plugin, without password hashes. The effective dump options close the file.

all.sql is the output of mysqldump --all-databases, the mysql system database included. A single-database source writes <name>.sql instead, with no USE statement, so it loads under any database name.

Snapshot 
5d2b81c7:/
├── manifest.json   # server, databases, tables, accounts
└── all.sql         # mysqldump --all-databases
plakar cat 5d2b81c7:/manifest.json 
{
  "version": 1,
  "connector": "mysql",
  "server_version": "8.4.3",
  "mysqldump_version": "mysqldump  Ver 8.4.3 for Linux on x86_64",
  "is_read_replica": false,
  "dump_format": "sql",
  "server_config": {
    "gtid_mode": "ON",
    "binlog_format": "ROW",
    "character_set_server": "utf8mb4"
  },
  "users": [
    { "user": "shop", "host": "%", "auth_plugin": "caching_sha2_password" }
  ],
  "options": {
    "single_transaction": true,
    "routines": true,
    "set_gtid_purged": "OFF"
  }
}

Under the hood

How Plakar runs mysqldump and mariadb-dump on production servers

exit status ≠ 0

Failed mysqldump runs never count as backups

When mysqldump stops with an error, the backup fails and reports the tool’s own message, so a truncated SQL file never passes for a good one.

--defaults-extra-file

MySQL passwords kept out of the process list

The password goes into a temporary option file that the client reads and Plakar removes when the command exits. It never shows up in ps or in the environment.

read_only = ON

MySQL and MariaDB backups from a replica

Point the source at a replica to keep the dump load off the primary. The manifest marks snapshots taken from a read-only server.

ssl_mode=verify_identity

TLS connections to MySQL and MariaDB

ssl_mode, ssl_ca, ssl_cert and ssl_key configure the connection, and the _data variants take the certificates inline.

column_statistics=false

A MySQL 8 mysqldump against an older server

column_statistics=false lets a MySQL 8 mysqldump dump an older server without querying a table that server lacks.

no_data=true

Schema-only and data-only MySQL dumps

no_data keeps the definitions without rows, no_create_info keeps the rows without definitions, and hex_blob writes binary columns in hexadecimal.

mysqldump to S3 and beyond: what Plakar adds to a cron job

Snapshots are encrypted on the backup host, so the bucket or SFTP server holds data it cannot read.

Read a manifest, compare two snapshots or mount one as a directory without restoring anything.

file servers · buckets · databases

The same CLI protects the application’s uploads, object storage and other databases next to MySQL, PostgreSQL or MongoDB among them.

Quickstart

How to back up MySQL or MariaDB with the open-source Plakar CLI

The Plakar CLI is free and open source. Install the integration, create a store, add the database as a source and a side database as a destination, then schedule the backup.

The MySQL and MariaDB CLI documentation lists the privileges the backup user needs and every option of the three protocols.

Shell 
$ plakar pkg add mysql
$ plakar at /var/backups create

$ plakar source add shop mysql://backup@db.example.com/shop \
    password=secret set_gtid_purged=OFF
$ plakar at /var/backups backup "@shop"
$ plakar at /var/backups check

$ plakar destination add shopside \
    mysql://root@db.example.com/shop_restore \
    password=secret create_db=true
$ plakar at /var/backups restore -to "@shopside" <snapshot_id>

Restore checklist

How to restore a MySQL or MariaDB backup: checklist

Read the manifest first. plakar cat <snapshot_id>:/manifest.json shows the server version, the dump tool, gtid_mode and the tables in the dump.

Snapshot the target before loading into it. A backup of the live database takes little space after deduplication and gives you a way back.

Restore next to production. Load the dump into a side database with create_db=true, then copy back only the rows or tables you need.

Use the client of the dump’s flavor. Restore a mysql:// snapshot with a mysql:// destination and a MariaDB snapshot with mysql+mariadb://.

Load whole-server dumps into a server of their own. An all.sql holds the mysql system database, so it rebuilds accounts and grants along with the data.

Check the restored tables before switching back. Run CHECK TABLE on them and compare SELECT COUNT(*) with what the application expects, then point the application at the data again.

FAQ

MySQL and MariaDB backup FAQ

Is mysqldump enough to back up MySQL?

mysqldump produces a consistent SQL copy. A backup also needs scheduling, history, encryption, a second location and a way to check the copies. Plakar runs mysqldump and provides the rest.

How does Plakar get a consistent MySQL or MariaDB dump?

With single_transaction=true, the default, InnoDB tables are dumped in one consistent transaction while the server keeps serving writes.

Do I still need backups if I run MySQL or MariaDB replication?

Yes. A replica applies a DROP TABLE or a wrong UPDATE as faithfully as any other statement. Replication covers the loss of a server, and a snapshot covers the loss of data.

How does a delayed MySQL replica compare with a backup?

A delayed replica covers a mistake noticed within its delay, and a snapshot covers a mistake found at any later date. On MySQL, CHANGE REPLICATION SOURCE TO SOURCE_DELAY=N holds each transaction back N seconds, 0 by default. Plakar snapshots keep every past state for as long as your retention allows.

How do I restore a dropped MySQL table?

Restore the last snapshot into a side database with a destination such as mysql://root@db/shop_restore create_db=true. Then recreate the table with CREATE TABLE ... LIKE and copy its rows with INSERT ... SELECT.

Should I back up one database or the whole server?

One database restores under any name, which suits targeted restores. The whole server captures every database plus the user accounts and grants. Many teams schedule both.

How often should I back up MySQL?

As often as your recovery point objective requires. An RPO of one hour calls for an hourly snapshot, and each run stores only the data that changed since the previous one.

How do I back up MariaDB?

Use mysql+mariadb://. It runs mariadb-dump for backups and mariadb for restores, with the same options as mysql://.

How do I back up MySQL to S3?

Create the Plakar store in an S3-compatible bucket and run the same plakar backup. The dump is encrypted on the backup host before it reaches the bucket, and only changed chunks are uploaded each night.

How do I fix “@@GLOBAL.GTID_PURGED cannot be changed” when restoring?

Set set_gtid_purged=OFF on the source, so the dump carries no SET @@GLOBAL.GTID_PURGED statement and loads into a server with its own GTID history.

Which mysqldump should the backup host use?

The one from the server’s own distribution. mysql:// calls MySQL’s mysqldump, mysql+mariadb:// calls mariadb-dump, and mysql_bin_dir points to a specific installation. The manifest records the binary behind every dump.

Does it work with managed MySQL services?

Yes. mysql:// connects to any managed MySQL that accepts a user over the network. Google Cloud SQL can also be reached by connection name with mysql+gcsql://, without running the Auth Proxy.

Which privileges does the backup user need?

For one database, SELECT, SHOW VIEW, TRIGGER and EVENT on it, plus PROCESS. For the whole server, the same on *.* with LOCK TABLES and RELOAD. The documentation has the GRANT statements.

How do I check a MySQL backup before restoring it?

Run plakar check to verify the snapshot, then plakar cat <snapshot_id>:/manifest.json to see the server, the databases and the tables it holds.

How do I see how a MySQL schema changed between two dates?

Compare the manifests of two snapshots with plakar diff <old_id>:/manifest.json <new_id>:/manifest.json. The unified diff shows the tables, columns, indexes and constraints added, changed or dropped between the two backups.

Can I back up MySQL from a replica?

Yes. Point the source at a replica to spare the primary. The manifest field is_read_replica shows that the snapshot came from a read-only server.

How much disk space does the backup host need?

Almost none for the dump. mysqldump writes to Plakar directly, and only the store grows.

Should I use the free CLI or Plakar Control Plane?

Start with the free, open-source CLI for a few servers. Move to Plakar Control Plane for discovery, policies and one view across many databases and teams. Both run the same MySQL integration.
